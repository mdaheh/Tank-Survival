# Архитектурный аудит «Tank Survival»

**Создано:** 2026-09-22 · **Обновлено:** 2026-09-25 · **Автор:** Cline (AI-агент Архитектор) · **Статус:** аудит + ремонт «Ф0R-5» (см. §9–§14); реализация ведётся по `tasks.md`
**База состояния:** коммит `697f507` (рабочее дерево чистое) — доказательства фаз привязываются к нему.
**Правила ролей:** `.clinerules` (роутер) + `ARCHITECT.md` (Plan) + `STANDART_EXECUTOR.md` (T1/T2) + `HEAVY_EXECUTOR.md` (T3/T4).

**Стек:** Unity 6000.5.9f1 · URP 17.5.0 · Input System 1.20.0 · uGUI + TextMeshPro · Post Processing 3.5.4 · цель — WebGL

> **Режим работы (мультиагентный):** **Архитектор** (Plan mode; правила — `ARCHITECT.md`) анализирует, проектирует, ведёт этот документ и `tasks.md` — production-код не пишет. **Исполнители** (Act mode; `STANDART_EXECUTOR.md` для T1/T2, `HEAVY_EXECUTOR.md` для T3/T4 — маршрут определяет поле `Исполнитель` в задаче) реализуют задачи из `tasks.md` и заполняют `Evidence`. Точка входа для любой сессии — короткий роутер `.clinerules`; если контекст потерян, читай этот файл и `tasks.md` вместо повторного исследования проекта. GigaCode выведен из стека (2026-09-25), один ИИ-контур на рабочее дерево.
>
> **Распределение правды:** целевая архитектура и обоснования — здесь; живой план работ, статусы и счётчик прогресса — **только в `tasks.md`** (раздел 8 этого файла — регламент передачи, дублировать чек-лист здесь запрещено).
>
> **Ключевые ограничения** (из `.clinerules`): производительность WebGL — главный приоритет (пулы, ноль аллокаций в кадре, статические батчи); сцена **никогда** не перезагружается между раундами; на экране **100–200+ врагов** и снаряды; в `Update/FixedUpdate` — никаких дорогих операций и аллокаций; каждое архитектурное решение — с Pros/Cons и влиянием на WebGL.
>
> **Суть геймдизайна** (актуальный `game_design.md`): модульный танк «Шасси + Турель»; турель автоматически атакует ближайшего врага; игрок управляет только перемещением и выбором улучшений; **до 5 типов врагов** (сейчас на диске 1), волны приходят **каждые n секунд с точек спавна**, состав/частота/количество зависят от сложности (3 сложности); враги **бьют при контакте**; при level-up выбор 1 из 3 улучшений; между забегами сохраняется только глобальный счётчик убийств (+ разблокировки); все числовые параметры — через ScriptableObject, новый контент — без изменения кода.

## 2. Критические проблемы интеграции (фактические баги)

Проверено по коду и ассетам (префабы, гуиды скриптов). Это не вкусовщины — места, где игра не работает или сломается в WebGL:

1. **Турель не монтируется в раунде.**
   `PlayerManager.SpawnTank()` ищет ребёнка `"TurretPos"`, но во **всех** префабах шасси (`body_standart`, `body_fat`, `body_fancy`, `body_veteran`) точка называется `"TurretMount"`. `PlayerPreview` ищет `"TurretMount"` (и его warning-текст врёт, упоминая «TurretPos»). Итог: в превью башня есть, в игре — `LogError` и возврат без турели.
   *Исправление: точка монтажа должна жить в данных (`ChassisData` — поле/компонент MountPoint на префабе), а не в строковых константах двух разных классов.*

2. **Враг неиграбелен.**
   Префаб `Prefabs/Enemy/Simple Enemy.prefab` содержит только `Transform + MeshFilter + MeshRenderer + CapsuleCollider + Rigidbody` — **нет** `EnemyAI`, `EnemyMovement`, `TankHealth`. `WaveManager.SpawnEnemy` молча пропускает (`if (move)`, `if (health)`, `if (ai)`) → враги стоят на месте, турель не стреляет (`Shooting.FindNewTarget` отбрасывает цели без `TankHealth`), враги не умирают → **волна никогда не завершается**.
   Плюс `TankHealth.Awake` → `Instantiate(m_ExplosionPrefab)` и `SetHealthUI()` со `Slider` — на врагах NPE/исключения, если добавить компонент без UI-обвязки. Нужен отдельный `EnemyData` и отдельная HP-логика врага без UI.

3. **`PauseMenu` перезагружает сцену.**
   `SceneManager.LoadScene(GetActiveScene().buildIndex)` в кнопке «Select Tank». При этом `DataCatalog.s_Initialized` — статический флаг: после перезагрузки он уже `true`, а `DataInitializer.Awake` защищён от повторного Init → **после рестарта каталог пуст**, все `Get...()` вернут null. Синглтоны пересоздадутся, статика — нет. Прямое нарушение правила «сцена не перезагружается».
   *Исправление: убрать `LoadScene`; возврат в меню = сброс состояния через FSM.*

4. **Улучшения «Урон/Взрыв» не работают.**
   `UpgradeOptionData.ApplyToPlayer()` делает `FindAnyObjectByType<ShellExplosion>()` и меняет `m_MaxDamage/m_ExplosionRadius/m_ExplosionForce` на **случайном существующем инстансе снаряда**. Следующие снаряды инстанцируются из префаба с дефолтами — бонусы теряются. `damageBonus` из `ShootingData` вообще нигде не применяется к урону. Бонусы обязаны жить в источнике (`RunContext`/`StatBlock`), а не в одноразовом инстансе.

5. **`ShellExplosion.OnTriggerEnter` → NPE на врагах.**
   `targetRigidbody.GetComponent<PlayerMovement>().AddExplosionForce(...)` без null-проверки — у врагов `PlayerMovement` нет.

6. **Сохранение на каждое убийство.**
   `GameManager.OnEnemyDied` → `SaveSystem.Save` (синхронный `File.WriteAllText`) на каждый kill; там же на каждый kill: `DataCatalog.GetAllChassis()`/`GetAllTurrets()`, которые **создают и сортируют новые List'ы** (GC на каждое убийство), и LINQ `Any()` внутри `PlayerProgress`.

7. **UI-аллокации в горячем цикле.**
   `GameManager.Update()` → `UpdateUI()` каждый кадр: `$"Убийств: {...}"` + присвоение `TMP_Text.text` → перегенерация меша текста и аллокация строк **каждый кадр**. `GameUIHandler.Update()` трогает `CanvasScaler.matchWidthOrHeight` каждый кадр. `LevelManager.Update()` — `xpBarFill.fillAmount` каждый кадр.

8. **Жёсткий хардкод против ГД.**
   `TOTAL_WAVES = 3`, «+5 врагов за волну», «×0.2 HP / ×0.1 скорости за волну», радиус спавна 15, XP за убийство = 10, пауза между волнами 3 с (`Invoke`) — всё в коде. По ГД число волн и состав зависят от сложности; XP зависит от типа врага. Нужны `WaveData`/`EnemyData` (их нет).

9. **Поражение недостижимо: у врагов нет контактного урона (ГД-разрыв).**
   В коде нет механизма урона игроку при касании — а ГД требует «идти к игроку, бить при контакте». `TankHealth.TakeDamage` игрока вызывается только из `ShellExplosion` (свои же взрывы). Событие смерти игрока никем не отслеживается: `GameManager.EndRound` срабатывает только после всех волн → условие «забег завершается немедленно, если игрок уничтожен» не реализовано.
   *Исправление (Фаза 0): минимальный компонент контактного урона на враге + сигнал смерти игрока в GameManager → EndRound.*

10. **Префабы не укомплектованы: компоненты и ссылки создаются рантаймом.**
    Проверено по гуидам: на 4 префабах шасси нет `PlayerMovement`/`TankHealth`/`TankInputUser` (добавляются `AddComponent` в `PlayerManager` при спавне), на 4 префабах турелей нет `Shooting` → после спавна `m_Shell`, `m_FireTransform`, `enemyMask` не назначены (выстрел невозможен), `TankInputUser` без `TankControl.inputactions` не подключает ввод (движение не работает). Аудио-поля `PlayerMovement` тоже пусты.
    *Исправление (Фаза 0): докомплектовать префабы сериализованными компонентами и ссылками; SO — только для числовых статов.*

**Мелкие, но реальные:**
- `DifficultyData.isUnlocked` дублирует флаги `PlayerProgress` — два источника правды;
- `WaveManager.StartWave` мутирует поля инстансов (`move.m_Speed *= ...`, `health.m_StartingHealth *= ...`) — работает, потому что инстансы свежие, но при пуле это станет багом (мутация возвращённых в пул объектов);
- `EnemyDeathListener` (`AddComponent` на каждый спавн + `UnityEvent` + подписка) — аллокации и хрупкость через `OnDestroy`;
- `Shooting.AutoAiming()` объявлен, но не вызывается; кэширование `Rigidbody` цели есть, но в цикле поиска — `GetComponent<Rigidbody>` + `GetComponent<TankHealth>` на каждый коллайдер;
- `GameManager` использует `Invoke(nameof(StartNextWave), 3f)` — магическая пауза, хрупко.

## 3. Отсутствующие модули (критичны для старта)

| Модуль | Статус | Почему критичен |
|---|---|---|
| Пул объектов | ❌ отсутствует | `Instantiate/Destroy` врагов, снарядов, частиц, карточек UI → GC-шторм на WebGL при сотнях объектов |
| Менеджер волн под ГД | ⚠️ заглушка | Нет `WaveData` (состав, соотношение типов, частота), нет данных о 5 типах врагов (по актуальному ГД) |
| Система «шасси+турель» | ⚠️ сломана | Монтаж по строковому имени, нет единой точки сборки, нет конвенции монтажа в данных |
| Реестр врагов (spatial) | ❌ | Поиск цели через `Physics.OverlapSphere`; нужен дешёвый источник «кто жив» без физики |
| Система урона (`IDamageable`) | ❌ | Один `TankHealth` с UI-слайдером тащит и игрока, и врагов — источник NPE |
| Прогрессия забега | ⚠️ | Бонусы применяются к компонентам напрямую, теряются при ре-спавне, нет единого хранилища статов |
| Ангар как экран | ❌ | Есть dropdown'ы в главном меню; по ГД нужен отдельный экран АНГАР с сохранением выбора |
| Событийная шина | ⚠️ | `UnityEvent` создаются/подписываются на каждый спавн — аллокации |
| Сохранение под WebGL | ⚠️ | `File.*` работает через IDBFS, но правильнее `PlayerPrefs` + сохранение в конце раунда |
| Комплектация префабов (ввод/оружие/HP) | ❌ | Компоненты и ссылки создаются рантаймом (`AddComponent`); снаряд, точка выстрела, маски и ввод не назначены — турель и движение игрока не работают (§2.10) |
| Контактный урон врагов | ❌ | ГД: «бить при контакте» — в коде отсутствует; поражение игрока недостижимо (§2.9) |
| `EnemyData` / `WaveData` | ❌ | Без них требование ГД «новые враги/волны без изменения кода» невыполнимо |

### 4.1 Классы и зоны ответственности

**Core**

| Класс | Ответственность |
|---|---|
| `GameManager` | FSM состояний, оркестрация: BeginRun → волны → Result. Без UI-кода и подсчётов |
| `RunContext` | Чистый объект забега: уровень, XP, `StatBlock`, выбранные id. Создаётся/сбрасывается, не статик |
| `StatBlock` | Аккумулятор модификаторов (урон, fireRate, скорость, HP…) — сюда применяются апгрейды; компоненты читают отсюда |
| `ScreenRouter` | Показ/скрытие экранов по состоянию FSM; замена россыпи `SetActive` в текущем `GameManager` |

**Data (SO)**

| Класс | Ответственность |

## 6. Ключевые решения: Pros/Cons и влияние на WebGL

**1. Пул: `UnityEngine.Pool.ObjectPool` vs кастомный.**
Рекомендация — `ObjectPool<T>` для компонентов (`EnemyView`, `Projectile`) + тонкий враппер с prewarm.
Pros: проверенный API, `CollectionCheck`, `actionOnGet/Release`, ноль кода владения. Cons: чуть больше абстракции. Кастомный пул даёт полный контроль, но это лишний код для соло-разработчика. Выигрыш на WebGL одинаков — главное убрать `Instantiate/Destroy` из цикла.

**2. Поиск цели: физика vs Registry.**
`OverlapSphere` на каждое оружие при сотнях врагов — аллокации + тяжёлый вызов физики. `EnemyRegistry` (обычный `List` + swap-remove) — перебор по обычной арифметике: на порядок дешевле физического запроса и без GC.
Cons: надо аккуратно поддерживать список при смерти/деспавне (решает `DamageSystem`).

**3. Сохранение: `File` vs `PlayerPrefs`.**
`PlayerPrefs` на WebGL — нативный и надёжный путь; JSON-строка внутри — тот же формат данных. Сохранение — только в конце раунда. Pros: без IDBFS-особенностей, меньше кода. Cons: лимит объёма — несущественно для нашего прогресса.

**4. События: `UnityEvent` на инстанс vs C#-event.**
`UnityEvent`, создаваемые/подписываемые на каждый спавн (текущий `EnemyDeathListener`) — аллокации на каждого врага. C#-события на `DamageSystem` — ноль аллокаций при постоянных подписчиках. Cons: нет Inspector-отображения — для симуляции не нужно.

**5. Физика врагов: Rigidbody vs кинематика.**
Сейчас каждый враг — `Rigidbody` c `Continuous` collision detection: при 200+ телах это убийство физического шага в WebGL. Предложение: кинематический `Rigidbody` (`MovePosition`) или вовсе без физики — движение трансформом + мягкое разведение через grid.
Pros: главный выигрыш по CPU. Cons: теряем физические «пробки» — заменяем намеренным сепарейшеном.

**Дополнительные WebGL-заметки:**
- статические батчи для `LevelDesert`, GPU instancing для одинаковых врагов;
- один общий SFX-пул с лимитом голосов вместо `AudioSource` на каждом снаряде;
- `sqrMagnitude` вместо `magnitude` в горячих путях;
- TMP: менять `text` только при изменении значения;
- IL2CPP без JIT: избегать boxing и LINQ в кадре.

## 7.1 Инцидент: правка ассета в обход Unity (закрыт правилом маршрутизации)

**Симптом.** Три отказа записи одного ассета — `Assets/Tank Survival/Prefabs/Enemy/Simple Enemy.prefab`. В `%LOCALAPPDATA%\Unity\Editor\Editor.log`:

```
File Assets/Tank Survival/Prefabs/Enemy/Simple Enemy.prefab couldn't be written.
Because moving <project>/Temp/UnityTempFile-<hash> to <project>/Assets/Tank Survival/Prefabs/Enemy/Simple Enemy.prefab
```

В отказах фигурирует только этот файл, других ассетов нет — дефект точечный, не системный. В проекте остались три незавершённых `Temp/UnityTempFile-*` — прямые следы неудачных подмен.

**Механика.** Unity не переписывает ассет на месте: сначала пишет новый файл в `<project>/Temp/`, затем подменяет (переименовывает) им старый. Подмена падает, если целевой файл открыт другим процессом так, что замена или удаление запрещены. Поэтому любой внешний «держатель» файла (текстовый редактор, дифф-вью, git-GUI, антивирус, импорт-воркер) даёт именно такую ошибку.

**Причина (по отчёту исполнителя).** У Стандартного исполнителя нет ни Unity, ни MCP-моста. Получив задачу с префабом в списке файлов, он пошёл по ассету напрямую — работал с YAML-файлом: читал его, искал компонент строкой, рассматривал создание `*.meta` со своим `guid` и правку ссылок на скрипт в тексте. Внешний инструмент держал файл — отсюда отказы подмены и «призрачное» состояние компонентов в редакторе (компонент виден в памяти, но в файле его нет).

**Снятые гипотезы (не подтвердились).**
- «Два писателя в одной Unity» — агенты у разработчика работают по очереди, а у исполнителя нет MCP.
- «Чужой MCP-клиент работал по префабу» — сообщение `[ManageAsset.GetComponentsFromAsset] … NullReferenceException` в логе принадлежит нашему собственному инструменту инспекции.
- «Гонка Unity с импорт-воркером или антивирус» — отказы привязаны ровно к одному ассету, который правил агент, а не к импорт-пайплайну. Три процесса `Unity.exe` в системе — это редактор и два его штатных `AssetImportWorker`, а не второй редактор.

**Урок.** Если у исполнителя нет легального инструмента для части задачи, а правила не дают явного стоп-пути, он находит обходной путь и рационализирует его. Поэтому запрет «не правь ассеты текстом» бесполезен без правила «остановись и выдай ТЗ».

**Принятое правило (внесено в `GIGACODE.md`, `HEAVY_EXECUTOR.md`, `.clinerules`, `tasks.md`).**
- Ассеты (`*.prefab`, `*.unity`, `*.asset`, `*.inputactions`, `*.controller`), сцена, инспектор, `ProjectSettings` — не работа исполнителей (ни Стандартного, ни Усиленного).
- Исполнителю запрещено: править и читать YAML ассетов, создавать и править `*.meta`, выдумывать `guid`, работать с Unity, MCP, сценой и инспектором.
- Ассетную часть выполняет человек или сессия с MCP-мостом; исполнитель выдаёт пошаговое ТЗ и не закрывает задачу до её выполнения (в «Заметках» — «код готов, ассетная часть: ТЗ»).
- Имена полей в ТЗ — только из кода (`Scripts/**`), состав объекта — только из MCP-инспекции, значения — из задачи или данных. Пример ошибки: в ТЗ исполнителя фигурировало поле «Health Per Wave», которого в `EnemyHealth` не существует.
- Конфиг агента (вне репозитория, `~/.gigacode_vsc/config/gigacode.jsonc`): `git checkout *` переведён из `allow` в `ask`, чтобы перезапись файлов рабочего дерева (в том числе ассетов) не проходила молча.

Поэтому ассеты, сцена и префабы теперь правятся **через MCP** — это штатный путь, а не исключение. Запрет сохранён только на правку текста/YAML ассетов, чтение YAML как источника данных, `*.meta` и выдуманные `guid`. ## 9. Контракты подсистем

**Правило одного владельца.** У каждого изменяемого состояния — **один** владелец и **одно** место сброса. Второй механизм — ошибка: он удаляется, а не дополняется третьим (именно так был сломан T024, §11).

| Подсистема | Владелец состояния | Право записи | Сброс / переиспользование |
|---|---|---|---|
| Пул объектов | `PoolManager` (обычный C# класс, `Instance`) | владелец пула через `actionOnGet` / `actionOnRelease` | **контракт `IPoolable.OnGetFromPool/OnReleaseFromPool`** (вводится в Ф0R-5) |
| Жизненный цикл врага | `PoolManager` + `WaveManager` | спавн/возврат только через `GetEnemy` / `Release` | `OnGetEnemy` (HP, скорость, слой) → `OnReleaseEnemy` (отписки реестра/DamageSystem, скрытие) |
| Снаряд | `PoolManager.m_ShellPool` | `Shooting.Fire` берёт, `Projectile` возвращает | `OnGetShell`/`OnReleaseShell` + сброс в `Projectile` (таймер, флаг детонации, коллайдер, базы радиуса/урона) |
| Статы танка | `RunContext.StatBlock` | только `UpgradeOptionData.ApplyToPlayer` (через `PlayerManager.Stats`) | `StatBlock.Reset()` при старте забега; базы перезаписываются из SO при `SpawnTank` |
| Урон и смерть | `DamageSystem` | оружие → `IDamageable.TakeDamage` | C#-события `OnEnemyKilled` / `OnPlayerKilled`, `EnemyHealth.DeathEvent` |
| Цель турели | `Shooting` (кэш `Transform` + `IDamageable`) | поиск раз в 0.5 с (`Physics.OverlapSphere`; Ф2 → `EnemyRegistry`) | кэш сбрасывается при потере цели |
| Прогресс | `PlayerProgress` | `GameManager` | накопление только счётчика убийств; save — в конце раунда (Ф3) |
| Прогресс в UI | `GameManager.GetPlayerProgress()` | чтение | **запрещено** второе `SaveSystem.Load()` в UI-классе (дефект найден в Ф0R-5 → T075) |
| Боеприпас/оружие | `TurretData` + префаб снаряда | `PlayerManager.ApplyTurretStats` → `Shooting` | база восстанавливается при взятии снаряда из пула, бонус идёт из `StatBlock` |

Как пользоваться таблицей: перед правкой любого переиспользуемого объекта первым делом ищи строку этой подсистемы. Нет строки — контракт не определён, задача возвращается Архитектору.

## 11. Разбор первопричины T024 (дефект пула снарядов)

**Симптом (из заметок исполнителя):** «`OnTriggerEnter` не вызывает взрыв, снаряд пролетает сквозь врагов и землю, бесконечно падает вниз». Исполнитель проверял физику (`Is Trigger`, `Use Gravity`, `Is Kinematic`, Layer Overrides, Collision Matrix) — всё было настроено верно, дефект лежал не там.

**Первопричина:** у снаряда **никто не сбрасывает состояние при взятии из пула**. `Projectile.OnGetFromPool` / `OnReleaseFromPool` объявлены `private` и **не вызываются ниоткуда** (проверено чтением: имена встречаются только в `tasks.md`). `PoolManager` использует собственные делегаты `OnGetShell` / `OnReleaseShell`, в которых сброса нет.

**Механика отказа (пошагово):**
1. `InitShellPool` прогревает 16 снарядов: создаются активными, сразу `Release` → `SetActive(false)`, коллайдер off. `m_Detonated = false`, **`m_LifeTimer = 0`**.
2. `UnityEngine.Pool.ObjectPool` внутри — **стек (LIFO)**: следующий `Get()` возвращает тот же объект.
3. Первый выстрел: `Update` → `m_LifeTimer (0) − dt ≤ 0` → **`Detonate()` сразу в стволе** (урона нет: `m_LastKnownTargetPos == Vector3.zero`), возврат в пул уже с **`m_Detonated = true`**.
4. Выстрел №2 берёт тот же объект; `m_Detonated` не сброшен → `Update` и `OnTriggerEnter` выходят на первой строке → снаряд летит до конца, проваливаясь сквозь триггеры (земля его не останавливает). Наблюдаемая картина совпадает с рапортом.

**Сопутствующие дефекты того же узла:**
- burst-эффект назначен на **дочерний** `Burst` внутри `CompleteShellExplosion`: родитель деактивируется в том же кадре после `ps.Play()` → взрыв не видно; `CancelInvoke()` в `ReturnToPool` отменяет `DisableBurstEffect`; требование «burst из пула, без unparent» не выполнено;
- звук не играет: `m_ExplosionAudio` — клип, но `AudioSource` ищется на `Burst`, а живёт на родителе `CompleteShellExplosion`;
- `Physics.OverlapSphere(..., ~0)` — аллокация `Collider[]` на каждый взрыв и потеря маски слоёв (регрессия настройки T055);
- fallback `Object.Destroy(gameObject)` при недоступном пуле — тихая деградация в обход пула; путь до пула идёт через `LevelManager.Instance.Pool`;
- сентинел `m_LastKnownTargetPos != Vector3.zero` — цель в мировом нуле не получит урон.

**Доказательства (факты, не гипотезы):** (1) чтение `Projectile.cs` — вызовов `OnGetFromPool` нет ни в одном файле; (2) MCP-инспекция префаба: `CapsuleCollider.isTrigger = true`, `Rigidbody.useGravity = true`, `m_LifeTime = 2`, `m_MaxDamage = 5`, `m_ExplosionRadius = 1`, `m_BurstEffect = Burst`; (3) иерархия префаба: `CompleteShell/CompleteShellExplosion/Burst` — эффект вложен в снаряд.

**Уроки постановки:** (а) в задаче отсутствовал **контракт владения состоянием** (§9) — «перепиши снаряд на пул» не отвечала на вопрос «кто сбрасывает состояние при взятии»; (б) проверка задачи требовала Play Mode, но была закрыта словами «проверка статическим анализом»; (в) `[x]` ставился без `Evidence`. Отсюда три процессных правила в §14.

## 11а. Находка T028: естественный цикл авто-огня не замыкается (гейт Ф1)

**Симптом (T028, `9ab4e8f`):** в естественном цикле враги наблюдаются на 15–62 ю при `fireRange=15`, поэтому `Shooting` почти не находит цель (2 выстрела за 30 с, 0 попаданий) и связка «авто-огонь → попадание → смерть» не замыкается. Контролируемый выстрел даёт попадание и урон (13.0 ю → HP 100→83.5) — снаряд исправен.

**Причина: не установлена.** Два кандидата: (а) движение врагов сломано/не подключено — дефект Ф1; (б) движение исправно, но точки спавна далеко и враги не успевают дойти — зона Ф2 (SpawnDirector T032). Статус: открыто, следующий шаг — T081.

**Прочие ⚠️ пункты T028 — расхождение областей, не дефекты:** A5 «XP начисляется» — Ф2/T033 (начисление отложено, `currentXp=0` ожидаемо); «возврат в меню» — Ф3/T041–T045; A6 «статы из StatBlock» — доказано T019/T025b/T025c. Пересмотренный смоук-тест — T082.


**Решение (T081, `b423d1d`):** причина — дефект Ф1 в `EnemyMovement` (бюджет поворота считался от `Time.deltaTime` одного кадра при вызове раз в 0,5 с ⇒ ~2°/с вместо 180°/с; враг уходил вдоль +Z, не доворачивая на игрока). Исправлено: сближение +10,65 ю/с, враг в `fireRange` 30/30 сэмплов. Находка закрыта; новый блокер T082 — §11б.

## 11б. Находка T082: радиус взрыва меньше дистанции контакта (гейт Ф1, 2-й заход)

**Симптом (T082, `bb51a81`):** подтверждённое прямое попадание при реальном `m_ExplosionRadius=1` даёт урон **0,00** (HP 100→100); тот же выстрел при `radius=3` — 16,50. Смерти от снарядов невозможны, естественный цикл не замыкается (2 снаряда за 43 с, 0 убийств), хотя фикс T081 подтверждён (враги сходятся, avg 3,5 ю).

**Причина:** `Physics.OverlapSphereNonAlloc` находит врага по **геометрии коллайдера** (сфера касается капсулы), а `CalculateDamage` меряет дистанцию до **`transform.position` (центра)**. Контактная дистанция до центра ≈1,02 задаётся положением снаряда в момент срабатывания триггера (капсула врага r=0,5, height≈1,41 — не «r=1»); при R=1 формула `(1−d/R)` даёт ≤0. Семантический баг «детект по поверхности, урон по центру».

**Лечение:** T083 — дистанцию урона мерить до `collider.ClosestPoint(center)` (поверхность) + рабочий `baseExplosionRadius = 3,0` в данных. Прямое попадание ⇒ d≈0 ⇒ полный урон; радиус = AoE-досягаемость от точки взрыва (не зависит от размера врага).

**Урок:** контролируемый замер обязан использовать **реальные данные** (радиус из `TurretData`), а не тестовые override'ы — прошлые прогоны (T024b/T024d/T028) гонялись на `radius=3` и маскировали дефект.
**Решение (T083, `d61d633`):** выполнено — `ApplyDamageTo` меряет `Distance(center, hitCollider.ClosestPoint(center))`, `baseExplosionRadius = 3,0`. Замер: прямое попадание 25,00 / сосед впритык 11,99 / за радиусом 0,00 (сходится с `(1−d/3)·25`); гибель за `ceil(HP/25)` попаданий. Блокер закрыт.

|---|---|
| **Burst — отдельный объект из пула** (`CompleteShellExplosion.prefab`), не ребёнок снаряда | прямое требование ГД «Пулы: … VFX»; убирает `Instantiate/Destroy` при десятках взрывов в секунду; эффект не «умирает» вместе с деактивацией снаряда |
| Эффект возвращается в пул **своим** компонентом по таймеру | `Invoke`/`Destroy` в пуле недопустимы: `Invoke` нельзя отменить при возврате, `Destroy` ломает переиспользование |
| **Убрать `Light` с корня снаряда** | 16 предпрогретых снарядов с реальным источником света в URP на WebGL = лишние проходы рендера; вспышка при необходимости — в эффекте (1–2 одновременно) |
| **`Rigidbody.useGravity = false`** у снаряда | сейчас при скорости 20 ю/с на `fireRange` 15 ю снаряд «ныряет» на ~2.8 ю и попадает только по вплотную подошедшим врагам; баллистики в ГД нет |
| `m_LifeTime = fireRange / speed + запас` — из данных | при текущих 2 с снаряд пролетает ~40 ю и падает на ~19 ю (наблюдалось как «бесконечно падает вниз») |
| **`ExplosionRadius` — данные:** `TurretData.baseExplosionRadius` + `StatBlock.explosionRadiusBonus` | ГД: параметры через SO/Inspector, новые турели без правки кода; в Ф2 поле переезжает в `WeaponBehaviorSO` вместе с типами атак |
| **`ExplosionForce` — удалить полностью** | это отбрасывание **самого танка игрока** (наследие туториала «два танка на арене»): в текущем ГД самотолкание своими же выстрелами + `Vector3.Lerp` каждый FixedUpdate + лишний `GetComponent` в попадании. Удаляем поле, апгрейд, вызов; мёртвый `EnemyMovement.AddExplosionForce` — тоже |
| Дистанционный falloff урона (`CalculateDamage`) — сохранить | «зрелищность» и AoE-радиус как способ уничтожения (ГД); формула не меняется, меняется только источник значений |
| `OverlapSphereNonAlloc` + переиспользуемый буфер + `LayerMask` | ноль аллокаций в попадании и возврат контроля слоёв, потерянного при переписывании |
| Числа боёвки — в SO/Inspector, дефолты префаба = fallback | ГД: числа не финальные; балансировка не должна требовать правки кода |
| Отброс врагов в ГД не требуется | если понадобится для «зрелищности» — отдельная задача с позиционным сдвигом (кинематические враги Ф4), а не физический импульс |
| Проверка «проходимости волны» = убийство всех врагов → смена волны (T082 A4), а не «танк выстоял стоя» | движение/уклонение — механика игрока, агентом не воспроизводится; «гибель стоя» — норма, не баланс-дефект |

## 14. Правила ролей и процессные изменения

| Файл | Кто читает | Содержание |

| `.clinerules` | все режимы, всегда | короткий роутер: режим → роль, маршрут по метке задачи, минимум чтения, инварианты, MCP-бюджет |
| `ARCHITECT.md` | Plan mode | артефакты Архитектора, контракты подсистем, формат задачи, сложность, гейты, права на файлы |

**Обязательные элементы процесса (введены 2026-09-25):**
1. **`Evidence`** в каждой задаче: «ожидалось → наблюдалось → как наблюдал». `[x]` без него не ставится.
2. **Статус `[-]`** — задача снята/заменена; в счётчик прогресса не входит.
3. **Поле `MCP: требуется / не требуется`**; при «требуется» — проверка моста до начала правок.
4. **Поле `Контракт`** для T3/T4 и всего, что меняет пул/статы/урон: владелец состояния и место сброса.
5. **Разделение кода и ассетов по владельцу**: код — Исполнитель, ассеты — тот же Исполнитель **через MCP** (или человек, если шаг не автоматизируется).
6. **Гейт по `commit hash`**: доказательство на незакоммиченном дереве недействительно.
7. **Минимальный сквозной прогон** перед смоук-тестом фазы (ловит класс «узел не работает», как T024).
8. **Разные модели на Plan и Act** (настройка Cline) — как «Стандартный/Усиленный»; Act-задачу лучше запускать в **новой сессии**, чтобы исполнитель не тащил контекст архитектора.
